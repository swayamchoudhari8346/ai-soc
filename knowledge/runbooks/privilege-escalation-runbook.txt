SOC RUNBOOK: Privilege Escalation Response (Linux)
Document ID: RB-002
Severity Scope: HIGH (successful escalation) / CRITICAL (root shell + persistence)
Last Updated: 2026-09-18

OVERVIEW
This runbook guides the SOC analyst through detecting, containing, and recovering from a Linux privilege escalation incident. Privilege escalation occurs when a user or process gains permissions beyond what was intended — most commonly a normal user obtaining root (UID 0) access.

Trigger conditions:
- Wazuh rule 5402: Successful sudo command execution (especially for sensitive operations)
- Wazuh rule 5404: Sudo session opened for root by a non-administrative user
- A normal user (UID > 999) accessing root-restricted files: /etc/shadow, /root/
- SUID binary execution not matching known-good baseline
- Linux auditd: execve of /bin/bash, /bin/sh with euid=0 from unexpected parent

---

PHASE 1 — TRIAGE (0–5 minutes)

1.1 Confirm and classify:
    - Is this an authorised admin performing routine work? Check the sudo log context.
    - Is the user account expected to have sudo access? Review /etc/sudoers.
    - Did the escalation use a known vulnerability or just misconfigured sudoers?
    - What did the user do after gaining elevated privileges?

1.2 Determine escalation path:
    a) Sudo abuse: user in sudoers with NOPASSWD or overly broad permissions
    b) SUID binary abuse: exploiting a setuid-root binary to gain shell
    c) Kernel exploit: CVE-based privilege escalation
    d) Credential theft: attacker obtained root password via brute force or credential dump
    e) Container escape: process escaped container to host root

1.3 Assess impact immediately:
    - Did the attacker read sensitive files? (/etc/shadow, private keys, database credentials)
    - Did the attacker create new accounts, SSH keys, or cron jobs?
    - Is the attacker still active on the system?

---

PHASE 2 — CONTAINMENT (5–20 minutes)

2.1 Isolate the host if root shell was obtained or active session is in progress:
    (AI action: isolate_host, L6 — REQUIRES ANALYST APPROVAL)
    - Network isolation prevents lateral movement and C2 communication
    - Use out-of-band access (console, IPMI) for post-isolation forensics

2.2 Kill the active privileged session if attacker is still present:
    (AI action: kill_process, L5 — REQUIRES ANALYST APPROVAL)
    - Identify the PID: ps aux | grep <username> or who
    - Kill the session: kill -9 <PID> or pkill -u <username>
    - Note: killing the session destroys in-memory evidence — capture first

2.3 Disable the compromised user account:
    (AI action: disable_account, L6 — REQUIRES ANALYST APPROVAL)
    - passwd -l <username>  (lock account)
    - usermod -e 1 <username>  (expire account)
    - Document the account status before change

2.4 Evidence preservation (do BEFORE isolation if possible):
    (AI action: collect_logs, L4 — automatic)
    - Capture: ps aux, who, w, last, netstat/ss -tnp, /var/log/auth.log
    - Capture bash_history for all users involved: /home/<user>/.bash_history, /root/.bash_history
    - Record all open files by suspicious processes: lsof -p <PID>
    - Memory snapshot if forensic tools available

---

PHASE 3 — INVESTIGATION (20–90 minutes)

3.1 Reconstruct the attack timeline:
    - When did the attacker first access the system?
    - What was the initial access method? (brute force, stolen credentials, web shell)
    - Which escalation technique was used?
    - What did the attacker do with root access?

3.2 Hunt for persistence mechanisms:
    CRON: crontab -l -u root; ls -la /etc/cron*; cat /var/spool/cron/*
    SSH KEYS: cat /root/.ssh/authorized_keys; find /home -name authorized_keys
    NEW USERS: grep ':0:' /etc/passwd (UID 0 accounts); check /etc/passwd modification time
    SERVICES: systemctl list-units --type=service | grep unknown
    SUID FILES: find / -perm -4000 -type f 2>/dev/null (compare to known baseline)
    LD_PRELOAD: check /etc/ld.so.preload; user .bashrc for suspicious exports
    ROOTKITS: rkhunter --check; chkrootkit

3.3 Assess data exposure:
    - What sensitive files exist on this host? (credentials, PII, intellectual property)
    - Were they accessed? Check auditd logs for open/read syscalls on sensitive paths
    - Were any files transferred out? Check outbound network connections during the incident window

3.4 Determine root cause:
    - Misconfigured sudoers? Document the rule and remediate.
    - Vulnerable SUID binary? Identify the binary and CVE.
    - Kernel vulnerability? Identify CVE, check patch level: uname -r
    - Social engineering / credential theft? Address the upstream access vector.

---

PHASE 4 — RECOVERY

4.1 Remove persistence mechanisms:
    - Remove any unauthorized SSH keys, cron jobs, new user accounts
    - Restore modified system binaries from trusted backup or package manager
    - Fix sudoers misconfiguration: remove NOPASSWD, restrict commands

4.2 Patch the vulnerability:
    - If SUID binary: remove SUID bit (chmod u-s <binary>) or patch the package
    - If kernel exploit: patch kernel (apt upgrade / yum update kernel) — schedule reboot
    - If sudoers: audit all sudo rules across the environment

4.3 Re-enable host (only after forensics are complete):
    - Verify no persistence remains (repeat hunt checklist)
    - Reset all credentials that existed on the host (root password, service account passwords, API keys)
    - Re-enable user account with new password and MFA if applicable
    - Remove network isolation

---

PHASE 5 — POST-INCIDENT

5.1 Escalation criteria (escalate to CRITICAL immediately):
    - Root account credentials confirmed stolen
    - Lateral movement detected to other hosts from this system
    - Cloud credentials or API keys exfiltrated
    - Evidence of ransomware deployment
    - Attacker had root access for >30 minutes before detection

5.2 Recommended hardening post-incident:
    - Audit ALL sudoers rules across the environment for NOPASSWD or overly broad grants
    - Deploy Linux auditd rules for privilege-sensitive syscalls
    - Enable Wazuh FIM on: /etc/passwd, /etc/shadow, /etc/sudoers, /root/.ssh/
    - Enforce principle of least privilege — remove unnecessary sudo access
    - Deploy PAM-based MFA for SSH and sudo
    - Set up process accounting (acct package) for full command history
